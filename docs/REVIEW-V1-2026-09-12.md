# PickUp 第一版产品与架构审查

审查日期：2026-09-12（Asia/Shanghai）

审查基线：`aa2064b`，应用版本 `0.1.0`；开始审查时工作区干净。

依据：[PRD v0.1](PRD.md)、[第一版原型](prototype.html)、[架构设计](ARCHITECTURE.md)、源码与本轮实际验证。

## 1. 验收结论

**第一版尚未全部完成，建议结论为“退回补齐后复验”，当前适合内部联调，尚未达到完整 MVP 的交付标准。**

已完成的主要成果是：真实 SQLite 业务后端、受限 IPC，以及覆盖记录、切换、恢复、整理、收尾的主窗口。F03/F04 的核心业务闭环已有端到端证据，事务与幂等处理也有较完整的集成验证。

主要缺口是：F01/F02/F07 的桌面系统集成尚未实现；快速记录关闭、收尾和详情可读性存在已复现问题；当前源码与现存分发产物不同；系统级、性能与安装升级验收尚未闭环。

PRD 第 12.1 节要求全部 P0 功能及 AC 通过。工程测试全绿只证明已有测试覆盖的行为。本次不以用例通过率换算产品完成率，也不把 P1/P2 的同步、手机、搜索、AI、数据导出算作首版欠交。

## 3. 已确认的问题与交接项

以下“高/中”是本次审查严重程度，与 PRD 的 P0/P1 范围定义分开。

### R01 · 高 · 桌面系统集成尚未交付

- **依据**：F01/F02/F07；AC-F02-01、AC-F02-03、AC-F05-03、AC-F07-04。
- **实际**：`src/main/index.ts:83` 只创建一个 BrowserWindow；`index.ts:106` 在全部窗口关闭时退出。主进程没有 Tray、globalShortcut、系统登录项应用、capture/widget 创建和窗口控制 API。
- `SettingsDialog.tsx` 只写数据库偏好，并明确说明系统操作尚未应用。`WidgetApp.tsx` 的记事/打开主窗口按钮显示待接入消息；有根组件不等于已经存在可用桌面入口。
- **影响**：在其他软件中记录临时事项、隐藏到后台继续使用，以及跨窗口确认当前任务的核心桌面体验尚未成立。
- **复验条件**：真实全局唤起与冲突提示、唯一 capture、widget 全部入口与位置/显示偏好、登录项读回、关闭隐藏及完全退出形成一个完整链路；覆盖重复启动、焦点恢复、多显示器和 DPI。
- **责任**：桌面工程；前端配合固定桥接和窗口生命周期。

### R02 · 高 · 直接关闭系统窗口会丢失尚未落盘的快速记录草稿

- **依据**：F01 草稿关闭规则、AC-F01-04。
- **复现**：打开“记一件事”→输入“关闭窗口前的未提交草稿”→在草稿的 300ms 去抖期间关闭原生窗口→重新启动并查询草稿。
- **实测**：关闭耗时 145ms；重启返回 `title: ""`、`note: ""`、`version: 0`，输入未被保留。见 `extra-results.json`。
- **根因**：`CaptureForm.tsx:84` 去抖保存；`tryClose` 的主动 flush 只连接模态关闭。`src/main/index.ts:106` 的原生窗口关闭路径没有等待 renderer 草稿落盘。
- **边界**：这不是已确认保存的任务丢失；是正常关闭流程中 PRD 明确要求保留的草稿丢失。模态内 Esc/关闭已有 flush，原生关闭仍欠缺。
- **复验条件**：输入后立即点标题栏关闭、Alt+F4、完全退出均先处理草稿；写入失败时保留输入并明确提示。
- **责任**：桌面与前端共同处理关闭协议。

### R03 · 高 · 收尾页持续打开时跨午夜不刷新

- **依据**：AC-F06-05；架构第 6 节要求可见收尾页安排一次性跨午夜刷新（`ARCHITECTURE.md:279`）。
- **复现**：建立 101 件当天完成事项并打开收尾；仅在隔离测试进程中将时间推进到次日，页面继续停留在收尾。
- **实测**：界面仍显示“当天完成 101”；同一应用此时重新查询已返回 `dayKey: 2026-09-13`、`total: 0`。见 `results.json.midnight`。
- **根因**：`DailyReview.tsx:89` 只在挂载、focus、visibilitychange 时读取，没有跨午夜定时刷新。日期查询逻辑正确，展示触发机制缺失。
- **复验条件**：持续打开跨日、重新显示、系统恢复和时区/时间变化后重新计算当天视图；全过程保持任务状态与断点不变。
- **测试边界**：本轮是进程内时钟模拟，未修改操作系统时间，亦未等待真实午夜。
- **责任**：前端主责，桌面负责系统恢复事件。

### R04 · 中 · 收尾的当天完成列表被截在 100 件

- **依据**：F06“各项数量均对应可打开的实际任务，不只展示统计数字”。
- **复现/结果**：创建并完成 101 件；标题显示 101，列表仅有 100 行，尾部提示“仅列出 100 / 101 条当天完成记录”，没有加载后续记录的操作。
- **根因**：`src/main/ipc.ts:36` 固定限制 100；`getDailyReview` 不接收后续分页参数；`DailyReview.tsx:229` 的 hasMore 只显示说明。
- **边界**：缺少的记录仍保存在数据库，也可去主窗口“已结束”分页寻找；收尾内清单本身不完整。
- **复验条件**：当天 101 件及更大样本，每件都能从收尾清单访问，数量与分页一致。
- **责任**：前端与接口/查询工程。

### R05 · 中 · 收尾中打开详情会丢失正在填写的断点

- **依据**：F06 要求在收尾检查事项、补断点；体验原则要求保留上下文。
- **复现**：有当前任务→收尾输入“审核草稿：下一步检查日志”→点一件事项打开详情→关闭详情→再次进入收尾。
- **实测**：断点输入为空。`results.json.reviewDraftAfterInspect` 为 `""`。
- **根因**：`MainApp.tsx:434` 将唯一 overlay 从 review 替换为 detail，收尾组件卸载；`DailyReview.tsx:37` 的草稿只保存在该组件局部状态，且详情关闭后没有回到原收尾上下文。
- **复验条件**：收尾内检查/编辑/完成事项后回到同一收尾上下文，未提交的断点继续保留。
- **责任**：前端。

### R06 · 中 · 详情的主要操作在浅色背景上接近不可辨认

- **依据**：PRD 11.2；设计规范要求操作可读和足够对比度。
- **实测**：正常启用的“标记等待”按钮文字为 `rgb(242,240,233)`，透明背景，所在侧栏是浅色纸面上的轻微灰色叠层。“完成”共用同类样式。见 `07-detail-contrast.png`、`extra-results.json.detailButton`。
- **根因**：`style.css:350` 的 `.btn-secondary` 使用深色页面所需的浅色文字；`style.css:1049` 只覆盖 `.modal-actions` 中的按钮，没有覆盖 `.detail-actions`。
- **复验条件**：未悬停、悬停、键盘焦点、禁用状态均清楚区分；当前/待处理/等待/已结束详情一起复验。
- **责任**：前端与设计。

### R07 · 中 · 窄窗口隐藏“今日收尾”的具名入口

- **依据**：F06 主动进入收尾；PRD 11.2 小窗口可用性。
- **实测**：原生窗口调整至 600×540 时，内容区为 588×478；“今日收尾”不可见。见 `04-small-window.png`。
- **根因**：`style.css:1408` 的窄屏规则将 `.sidebar-bottom` 隐藏（1436 行），收尾按钮正位于该区域。
- **边界**：功能仍可经恢复区域 Next start 的“选择/更换”间接进入，因此不是收尾功能完全失去访问路径；但用户看不到明确的收尾入口，发现成本明显增加。
- **复验条件**：最小窗口下仍保留可见且名称明确的收尾入口，并验证缩放后的导航。
- **责任**：前端与设计。

### R08 · 高（交付门槛）· 现存分发产物与本次源码基线不同

- `dist/win-unpacked/resources/app.asar` 内 renderer 为 `index-sOtn9XyX.js`；本轮构建为 `index-jaRAxl4W.js`。主进程内容哈希相同，但前端不同。详见 `package-comparison.json`。
- 现存 NSIS 安装包 `PickUp Setup 0.1.0.exe` 的本机最后写入时间为 2026-09-10 11:37:34；解包目录记录为 2026-09-11，均早于 2026-09-12 前端提交。
- **结论**：本轮源码测试结果不代表这些旧产物包含当前前端；现存安装包也缺少与当前提交绑定的完整验收记录。
- **复验条件**：从拟交付提交生成新产物，记录提交/版本/哈希；对该产物执行 E2E，并完成安装、卸载保留数据、覆盖升级和离线运行验证。
- **边界**：本轮仅检查旧产物，不覆盖重打包，避免把审核变成新的版本发布。
- **责任**：交付/桌面工程与测试。

## 5. 设计与架构评价

### 设计

- 已实际查看本轮主界面、设置、详情、长文本、小窗口截图，并渲染第一版原型进行对照。深色网格背景、荧光黄与纸色卡片、左导航、当前卡片/收件入口、下方任务/恢复区的主视觉均保留。
- 正式版去掉示例任务和固定日期，改接真实任务/本地日期；移除原型持续波形动画，符合架构的安静桌面要求，不应算漏做装饰。
- 第一版原型含外部图标 CDN；本次原型截图屏蔽网络，故其中缺少图标。正式应用图标来自本地 lucide-react。原型截图只用于布局/配色对照，不作为图标验收依据。
- 设计尚未验收通过：详情按钮对比度 R06、窄窗口收尾入口 R07，以及桌面独立窗口 R01 仍需完成。
- 长标题使用 184 字符连续英文，长备注使用 200 组中文短句；详情 `clientWidth` 与 `scrollWidth` 均为 705，没有横向溢出。此结果只覆盖该样本，不扩展为全部长文本或全部 DPI 已验收。
- 本轮截图来自隐藏 Electron 窗口的实际渲染；未做真实输入法、屏幕阅读器、系统缩放切换和人工窗口拖动走查。

### 架构

- 层次与既定方向一致：React renderer → 固定 preload → main 的来源/参数校验 → 单 worker → SQLite；未引入额外 HTTP 后端。
- 关键一致性已有代码与测试支持：唯一 doing 索引、同步短事务、commandId 回执先行、expectedVersion、revision、下次开工引用清理、稳定排序、故障回滚。
- `contextIsolation`、禁用 Node 集成和 sandbox 已检查；业务通过固定 API；本轮现有 E2E 覆盖 renderer 隔离。这里不是全面安全审计结论。
- 系统偏好只持久化但未对 OS 应用、关闭路径缺草稿 flush、收尾缺日期失效机制，是当前边界落地的主要不足；无需据此重做整套技术架构。
