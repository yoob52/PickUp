## 1. 职责目标

将现有产品和架构材料转化为开发人员能够领取、实现、联调和验收的工程基线。我的责任是明确范围、接口、版本、任务依赖和质量标准，并跟进高风险项的验证结果。

这包括为确定技术方案而进行必要的工程初始化和最小验证；完整功能实现分别落到桌面、数据、前端等开发职责。测试职责执行独立验收，产品/设计职责补齐交互决定。团队人员可兼任，责任边界仍需明确。

“文档写好”“配置写好”“开发环境跑通”“安装后验证通过”分别记录，不能互相替代。当前已有 PRD 和架构文档，不代表版本组合、工程脚手架或安装包已验证。

## 3. 逐项工作内容及完成标准

### TL-01：收敛需求与设计差异

需要完成：

- 核对 F01—F07、全部 AC 条目和未写成 AC 的功能规则，确保没有遗漏的 P0。
- 整理原型中 nextUp 自动变化、暂停排序、日期固定、备注草稿、收尾清单、桌面入口等差异，注明正式实现依据。
- 区分“用户已确认”“架构默认值”“需要产品决定”“需要技术验证”，不把默认值写成确认结论。
- 明确新增断点、等待原因、重新打开、历史完成与当日统计之间的字段与行为关系。
- 补齐需要开发执行的参数：标题/正文输入限制及提示、列表分页、快捷键默认值、窗口尺寸约束、草稿保存和关闭语义。影响用户体验或范围的限制标为建议，由产品职责落实。
- 统一 M1/M2 边界：M1 用最小界面验证保存、切换和恢复链路；完整的交互及全部边界验收在 M2/M3 完成。

完成标准：每个差异都有处理结论或明确的决策责任与截止阶段；技术任务没有依赖未标注的隐含产品规则。架构变更同步写回 ARCHITECTURE.md，避免另建冲突基线。

### TL-02：明确接口与数据契约

需要完成：

- 逐一列出 renderer → preload → main → worker 的允许方法与调用方权限。
- 定义每个命令的输入、返回值、字段约束、预期任务版本、错误码及其界面处理方式。
- 明确 requestId、commandId、revision、task.version 和草稿/偏好版本各自的用途。
- 定义“需要切换”“状态冲突”“保存失败”“结果待确认”的响应和重试流程。
- 明确命令回执去重、payload 规范化、过期编辑以及多窗口消息乱序处理。
- 定义工作区快照、分页列表、详情、收尾查询的字段，避免主窗口自行推导另一套业务规则。
- 核对数据库 schema、初始值、迁移顺序、状态历史和核心事务；将共享接口落到 TypeScript 类型和运行时 schema，作为后续实现的唯一契约来源。

完成标准：前端可以据此生成模拟响应并开发交互；主进程和 worker 能独立实现同一接口；每个修改命令至少具有正常、冲突及失败场景说明。契约通过类型检查后，后续文档只补充语义，不重复维护另一份类型定义。

### TL-03：锁定依赖和验证相容性

需要完成：

- 检查开发机 Node.js/npm、操作系统和构建工具条件。
- 核对 Electron、React、TypeScript、electron-vite、better-sqlite3、electron-builder 与测试工具的版本要求，从官方资料选定相容稳定版本。
- 记录开发 Node.js 与 Electron 内置 Node.js 的差异，验证原生数据库模块与 Electron 目标架构匹配。
- 确定唯一的原生依赖重建入口、安装失败处理方式和构建机额外工具要求。
- 生成并提交 package-lock.json，记录已验证的精确版本；通过实际安装和加载验证后再标为锁定基线。

完成标准：从锁文件可以安装依赖，Electron 运行时中可以启动 worker、加载 SQLite 并完成读写。记录命令、环境和结果；单纯查询到版本号不算相容性验证完成。

### TL-04：建立工程和协作规范

需要完成：

- 落实 main、preload、worker、renderer、shared 的目录和导入边界。
- 配置 TypeScript strict、各运行环境的类型范围、构建入口及 worker 输出路径。
- 约定命名、错误处理、日志内容、配置读取、时间/ID 生成、SQL 迁移和版本管理方式。
- 建立开发、类型检查、静态检查、单元测试、Electron 集成测试、构建和打包命令。
- 隔离开发、测试和正式 userData，避免验收或故障注入访问用户正式库。
- 明确新增依赖、共享契约修改、数据库变更和代码评审要求。
- 定义持续集成应执行的检查；实际代码托管平台未确定时，先提供本地可运行的同等命令，不虚构远程流水线状态。

完成标准：文档中的命令真实存在且对应工作可执行；所完成的初始化范围能从干净依赖环境复现。未实现的功能测试标为待完成，不用空测试或跳过测试制造通过记录。

### TL-05：拆分开发任务和安排依赖

需要完成：

- 按可验收交付拆分工程、数据、桌面、前端和测试任务，避免使用“完成前端”“完成数据库”一类不可独立验收的大任务。
- 每项任务写明编号、目标、对应 F/AC、责任角色、前置任务、涉及模块、工作项、交付物、验收方法与风险。
- 把失败、空状态、中文输入法、跨日、多窗口和重启恢复分配到具体任务，不作为最后统一补充的模糊工作。
- 给出首批可立即领取的任务和后续解锁条件；共享契约先行，再安排可以独立推进的工作。
- 估算时说明人员熟悉度、验证成本与不确定性；未知人员配置下不承诺日历工期，M1 后修正剩余估算。

完成标准：每个 P0 功能/AC 都能追溯到实现任务和测试任务；任务依赖无循环；领取任务的人能明确判断何时完成。各角色可以由同一人兼任，本计划不代表已经向其他人员派单。

建议任务卡字段：

| 字段 | 内容要求 |
| --- | --- |
| ID / 标题 | 稳定编号 + 可交付目标 |
| 需求关联 | F 编号、AC 编号、补充架构约束 |
| 负责人 | 责任角色；人员确定后再填姓名 |
| 前置依赖 | 任务编号或已落实的决定 |
| 工作内容 | 可执行操作与涉及模块 |
| 交付物 | 文件、行为或验证记录 |
| 验收 | 操作步骤、预期结果、自动或人工检查 |
| 风险/估算 | 影响范围、假设及待验证项 |
| 状态 | 待开始 / 进行中 / 待验证 / 完成 / 阻塞及原因 |

### TL-06：制定质量门槛和联调流程

需要完成：

- 建立 PRD 中 33 条 AC 的逐条追踪表，并补充功能正文中的规则和非功能需求。
- 明确纯逻辑、组件、真实 SQLite 集成、Electron 端到端和 Windows 人工专项的测试分工。
- 定义核心数据风险测试：事务中途失败、提交成功但响应丢失、重复请求、旧版本修改、多窗口竞争、迁移失败、异常退出。
- 定义原生库/worker 的安装后检查、升级保留数据和正式数据目录隔离检查。
- 定义性能样本、测量起止点和环境记录方式；沿用架构中的 PRD 指标，其他阈值依据实测确定。
- 规定合并、阶段交付和发布三个层次的完成条件；问题需记录责任和复现方法。

完成标准：每个检查有输入条件、步骤、期望结果和执行方式；可以区分“设计完成”“功能实现”“自动检查通过”“实机验收通过”。数据可靠性和全部 P0 仍是发布门槛。

### TL-07：落实关键技术验证

需要完成的验证闭环：

1. 安装后的 Electron 程序启动 worker，创建任务、保存 SQLite、退出重启后读取。
2. 注册全局快捷键，唤起 capture 并输入中文；重复按 Enter 不重复创建。
3. 以最小界面执行 A → B 切换，验证断点和状态一起提交，多窗口看到一致结果。
4. 注入提交前失败和提交后响应丢失，验证回滚及原命令重试。
5. 主窗口隐藏、托盘恢复、第二次启动、完全退出和 widget 可见区域恢复。
6. 生成并安装完整包，验证原生库、资源路径和 worker 路径；记录热唤起、保存和总进程资源数据。

我的责任是提供验证方案、完成必要的最小实现或明确开发任务、审核结果并更新架构。涉及系统集成的检查以实际工具和设备条件为准，未执行项明确记录；不能只凭网页文档宣称通过。

完成标准：产出可复现步骤与证据，关键方案能在目标安装环境运行；失败项明确影响和处理决定。M1 验证完成不等于全产品完成。

### TL-08：交接及持续跟踪

需要完成：

- 汇总“从哪里开始、调用什么接口、改哪些模块、如何验收”的开发入口。
- 给桌面/数据/前端/测试职责明确首批任务、依赖和联调时间点；给产品/设计职责提供具体缺口清单。
- 根据 M1 结果调整任务粒度、估算和技术风险，持续维护阻塞项。
- 在共享契约、数据迁移、状态事务和打包边界的变更中执行技术评审；对正常局部实现给予开发者自主空间。
- 维护需求 → 任务 → 检查 → 结果的追踪，发布前评审剩余问题和 P0 完成情况。

完成标准：开发者无需自行猜测架构即可开始首批任务；已知未决项各有责任和处理节点。交接完成之后，质量评审和风险跟踪继续贯穿 M1—M4。

## 6. 我可直接决定和需要协同的事项

我负责直接落实：模块边界、接口组织、锁文件、错误码、事务与幂等方案、测试分层、任务粒度、构建入口，以及既有架构范围内的技术实现选择。

产品/设计职责需要协同：widget 的尺寸和收起形态、失败/冲突界面及文案、影响输入体验的硬限制、每日统计口径若有变更。先列出明确建议和影响，不反复要求确认已决定的技术栈。

交付方需要落实：实际支持设备、正式分发渠道、签名条件和是否提前纳入数据导出/备份。按 Windows 11 x64 默认值可以推进开发准备；对外承诺前落实目标范围。

本轮仅整理职责和计划，没有调整系统设置、安装依赖、创建远程任务或开始全量产品实现。

## 7. 总体验收标准

技术负责人本阶段工作在以下条件满足时完成交接：

- 全部 P0 与 AC 已映射到具体开发/测试任务，依赖可执行。
- 模块职责、IPC 和数据语义足够明确，关键规则没有互相冲突的定义。
- 工具链版本与工程配置通过实际复现验证，安装环境关键技术有验证结果。
- 开发、测试、正式数据隔离；故障和恢复检查有具体方法。
- 阶段完成标准与发布标准明确区分，未完成和未决事项透明可见。
- 下一位开发者可以领取第一项任务并知道具体交付与验收要求。

本计划是上述工作的起点，后续以各项实际产出和验证记录判定完成。
